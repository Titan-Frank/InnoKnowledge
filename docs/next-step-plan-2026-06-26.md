## 一、总体判断

OKM 现在已经不是一个单纯的知识图谱抽取脚本，而是正在变成“面向 AI 使用的知识基础设施”。这个方向可以概括为三层：

1. 底层是统一知识图谱：用 `world_nodes`、`world_edges`、`world_evidence`、`world_domain_profiles`、`world_node_cards` 等表保存可验证的知识结构。
2. 中层是知识单元视图：按 `node_id` 把节点、关系、证据、领域画像、卡片、正文聚合成一个可被前端、检索、生成系统调用的知识单元。
3. 上层是知识运行能力：不只查询知识，还要让智能辅导系统、教材生成、学习路径、评价任务能稳定调用这些知识对象。

当前代码库最强的基础在第一层：TypeScript 抽取管线已经围绕 `server-pipeline-run`、`staging`、`merge`、`normalize`、`strict-qa`、`graph-integrity` 建成。下一步不应该再重写主流程，而应该在现有多表图谱上补齐消费侧能力：正文层、外部知识单元导入、对象级检索与生成验证。

一个关键架构原则需要固定下来：

> 知识单元不是生产侧中间状态，而是消费侧聚合视图。PDF 或 Markdown 教材仍然直接进入 OKM 抽取管线；外部已有知识单元、Obsidian 笔记或其他知识库才走外部导入路径。

这点很重要。否则会把已经清楚的生产流程拉长，造成重复去重、上下文丢失和维护成本上升。

## 二、当前代码库状态

### 已经具备的能力

1. TypeScript 工作区已经成型：
   - `packages/types`：共享类型。
   - `packages/pipeline`：抽取、暂存、合并、归一化、检索、质检。
   - `packages/server`：接口服务和 PostgreSQL 查询。
   - `packages/viewer`：图谱可视化和节点详情。

2. 生产侧主流程已经明确：
   - `npm run server-pipeline-run -w packages/pipeline`
   - `strict-qa`
   - `graph-integrity`
   - `backfill-embeddings`
   - `cluster-nodes`

3. 统一知识体系已经落在数据库结构中：
   - 顶层本体：9 类 `kind`。
   - 事实关系：15 类 `world_edges.type`。
   - 领域画像：`world_domain_profiles`。
   - 证据与溯源：`world_evidence`、`world_evidence_links`、`world_mentions`、`world_node_cards`。
   - 向量字段：`world_nodes.embedding vector(2560)`。

4. 服务端和前端已经有知识单元视图雏形：
   - `packages/types/src/models.ts` 已有 `ApiUnit`、`ApiUnitBody`、`ApiUnitMedia` 这些知识单元相关类型。
   - `packages/server/src/routes/unit.ts` 已有 `/api/source/:key/unit/:node_id`。
   - `packages/server/src/db/queries.ts` 的 `loadUnit` 已按节点聚合关系、画像、提及、证据、媒体、原文片段、卡片。
   - `packages/viewer/src/components/sections/DetailUnit.tsx` 已能展示知识单元详情、课本原文、图片和关系。

### 仍然缺的关键能力

1. `world_node_bodies` 正文表、正文结构规则、类型、正式正文读取、生成命令和正文质检已经补齐，后续需要接真实数据跑一批正文生成。
2. 知识单元视图还需要进一步稳定成公开契约。它已经能用，但导出格式和 API 文档还需要补齐。
3. 外部知识单元导入还没有实现。尤其是 Obsidian 笔记到 OKM 多表结构的映射、对齐、合并、冲突复核还没有工程入口。
4. 对象级检索还停留在管线候选检索和前端查看层，尚未形成可评测的“对象级检索 + 语义规划 + 生成”闭环。
5. 研究评价体系还没有落成可运行脚本。报告里提出了对象质量、关系质量、证据覆盖、生成可靠性等指标，但还没有变成评测基准。

## 三、下一阶段的主线目标

未来三个月的目标不应是“大而全地实现 AI 原生知识系统”，而是完成一个可验证闭环：

> 选定一个边界清晰的 K12 教材或知识范围，构建 100 到 300 个可追溯的知识对象；补齐知识单元正文层；支持对象级检索和详情展示；用小规模人工标注评测抽取质量和对象级生成质量。

这个闭环对应四个工程成果：

1. 可持久化的知识单元正文层。
2. 稳定的知识单元 API 和 Viewer 展示。
3. 外部知识单元 / Obsidian 笔记导入原型。
4. 对象级检索与语义规划生成的最小实验。

## 四、阶段一：补齐 `world_node_bodies`

> 2026-06-26 完成记录：已新增 `world_node_bodies`、`schemas/world-node-body.schema.json`、`ApiUnitBody` 更新、Unit API 正文读取、`generate-node-bodies` 管线命令、正文质检规则和 Viewer“知识正文”展示。2026-06-27 已废除卡片临时回退，缺少持久化正文时 `body` 为空。

### 目标

让知识单元不再只靠卡片临时拼正文，而是拥有独立、可追溯、可渲染、可扩展的正文层。

### 为什么先做这个

报告和计划都把“完整知识正文”视为当前 OKM 最明显的缺口。卡片适合做结构化摘要，但不适合承载课文原文、现代文翻译、词语注释、图示说明、公式推导、案例分析、跨链接等连续内容。没有正文层，后续的 Obsidian 导入、语义规划、对象级生成都会缺少上下文。

### 建议任务

1. 设计 `world_node_bodies` 表。
   - 主键：`dataset_id, node_id`。
   - 字段：`format`、`content`、`media_refs_json`、`source_refs_json`、`generated_from`、`status`、`created_at`、`updated_at`、`properties_json`。
   - 外键：引用 `world_nodes(dataset_id, id)`。
   - 初期只支持 `markdown`。

2. 增加结构规则和类型。
   - 新增 `schemas/world-node-body.schema.json`。
   - 更新 `packages/types/src/models.ts` 中的 `ApiUnitBody`，让它和数据库字段一致。

3. 更新服务端知识单元查询。
   - `loadUnit` 只读取 `world_node_bodies`。
   - 如果没有持久化正文，`body` 返回空，不再临时展开 `world_node_cards`。
   - 返回值明确标记 `generated_from`，区分 `manual`、`card_expansion`、`model_generation`、`imported_unit`。

4. 增加正文生成入口。
   - 新增管线命令，例如 `generate-node-bodies`。
   - 第一版只做卡片到 Markdown 正文的扩展。
   - 模型模式根据节点信息、高质量卡片、课本原文片段和证据引用生成正式正文。
   - 生成结果必须带 `source_refs_json`，不能生成无来源正文。

5. 更新 Viewer。
   - 详情页把“节点说明”改成真正的“知识正文”。
   - 保留卡片区域，用于展示结构化摘要。
   - 正文中的图片引用优先通过 `media_refs` 和证据解析。

6. 增加质量检查。
   - `strict-qa` 增加可选检查：正文存在时，`source_refs_json` 必须非空。
   - 检查正文引用的证据是否存在。
   - 检查 Markdown 图片引用是否能解析到允许访问的资源。

### 验收标准

1. 一个已有节点可以从 `world_node_bodies` 读取正文并在 Viewer 中展示。
2. 没有正文的节点不显示“知识正文”，避免把结构化卡片误当成正式正文。
3. `npm test -w packages/pipeline`、`npm run check`、`npm run build` 通过。

## 五、阶段二：固定知识单元视图契约

### 目标

把当前已经存在的知识单元视图从“能展示”推进到“可作为上层系统稳定调用的 API”。

### 建议任务

1. 明确 `ApiUnit` 的字段边界。
   - `node`：身份与本体层。
   - `relations`：入边、出边。
   - `domain_profiles`：领域投影。
   - `evidence`：证据。
   - `source_fragments`：原文片段。
   - `card`：结构化摘要。
   - `body`：连续正文。
   - `media`：图片等媒体资源。

2. 写知识单元 API 测试。
   - 覆盖有正文、有卡片、只有原文片段、含图片证据、含入边和出边的样例。

3. 增加导出格式。
   - 提供 `unit.json` 风格的导出结构。
   - 为后续对象级检索、生成、数据集发布复用。

4. 建立文档。
   - 在 `docs` 中补一份知识单元 API 说明。
   - 明确知识单元是消费侧视图，不是抽取中间层。

### 验收标准

1. `GET /api/source/:key/unit/:node_id` 返回结构稳定。
2. 前端详情页只依赖公开字段，不依赖临时字段。
3. 知识单元导出结果可以作为评测样本和生成上下文。

## 六、阶段三：实现外部知识单元 / Obsidian 导入

### 目标

让外部已有知识单元进入 OKM，并和已有图谱对齐。这里的外部知识单元包括其他系统导出的结构化知识、手动整理的 Markdown、Obsidian 笔记。

### 需要纠正的一点

外部导入不是“PDF 先转知识单元再转 KG”。PDF 仍走现有教材到图谱管线。

外部导入也不应该绕过归并器直接写 canonical 表。根据当前代码库规则，课时工作器只能写暂存表，canonical `world_*` 写入、去重、重映射和最终质检应放在归并步骤。外部知识单元导入可以新增导入暂存表，也可以复用现有 `world_staging_*` 思路，但最终合并必须由归并器控制。

### 建议任务

1. 定义外部知识单元输入格式。
   - 支持 `id`、`name`、`kind`、`definition`、`aliases`、`domains`、`tags`、`relations`、`body`、`source_refs`。
   - `tags` 只做检索辅助，不承担主分类职责。

2. 设计 Obsidian 解析规则。
   - 标题映射为 `name`。
   - frontmatter 映射为分类和标签。
   - 正文映射为 `body.content`。
   - Wiki 链接映射为候选关系或候选引用。
   - 本地图片映射为 `media_refs` 或证据。

3. 做结构映射。
   - 外部知识单元到 `world_nodes`、`world_edges`、`world_evidence`、`world_node_bodies`、`world_domain_profiles` 的映射必须显式配置。

4. 做对齐与冲突判断。
   - 使用名称、别名、定义、embedding、语义 key 组合打分。
   - 高置信合并，低置信新建，中间区间进入复核。

5. 接入归并器。
   - 不直接散写 canonical 表。
   - 复用或扩展 `merge` 模块的合并逻辑。
   - 复核决策可以进入 `world_canonical_node_map` 或新增导入复核表。

6. 做端到端样例。
   - 选 10 到 20 篇 Obsidian 笔记。
   - 跑：解析、映射、对齐、合并、质检、Viewer 查看。

### 验收标准

1. 一篇 Obsidian 笔记能进入知识单元视图并保留正文。
2. 已存在概念不会重复创建节点。
3. 冲突样例能进入复核，而不是自动误合并。
4. 导入后 `strict-qa` 和 `graph-integrity` 通过。

## 七、阶段四：对象级检索与语义规划生成

### 目标

在不训练新模型的前提下，先验证“知识对象比文本片段更适合支撑可靠生成”。

### 建议任务

1. 固定对象级检索输入输出。
   - 输入：用户问题、领域、学段、目标任务。
   - 输出：相关知识单元、关系路径、证据、正文片段。

2. 实现语义规划格式。
   - 规划不是自然语言长篇推理，而是知识单元和关系路径的有序列表。
   - 每一步要能追溯到节点、边或证据。

3. 增加生成入口。
   - 输入语义规划和知识单元正文。
   - 输出解释、例题、学习路径或课堂活动。
   - 输出中保留使用了哪些知识单元和证据。

4. 做三组对比。
   - 纯模型回答。
   - 普通文本片段检索回答。
   - OKM 对象级检索回答。

5. 评测指标。
   - 事实准确率。
   - 引用准确率。
   - 证据覆盖率。
   - 幻觉率。
   - 前置知识遗漏率。
   - 教学解释可用性。

### 验收标准

1. 至少 50 个问题形成评测集。
2. 每个回答能列出使用的知识单元和证据。
3. 对象级检索相对普通文本检索至少在可追溯性和证据覆盖上有明显优势。

## 八、阶段五：构建小规模评测基准

### 目标

让 OKM 的研究路线具备可复现实验基础，而不是只有系统演示。

### 建议范围

先选择一个稳定、边界清楚、教材结构完整的范围，例如：

1. 初中化学一个单元。
2. 高中物理基础力学。
3. 人工智能导论的一组核心概念。

### 最小数据规模

1. 快速迭代集：50 个节点，100 到 200 条边。
2. 正式小评测集：200 个节点，500 条边。
3. 长期公开数据集：2000 个节点以上，5000 条边以上。

### 评测内容

1. 节点 F1：节点抽取质量。
2. 关系 F1：关系抽取质量。
3. 类型准确率：9 类本体分类准确率。
4. 先修一致性：先修关系无环和方向合理性。
5. 证据召回率：节点和边的证据覆盖率。
6. 知识单元完整度：知识单元中正文、卡片、证据、关系是否完整。

### 验收标准

1. 有人工标准标注文件。
2. 有评测脚本。
3. 有至少三个基线：
   - 规则基线。
   - 直接模型抽取基线。
   - OKM 当前管线。
4. 有错误分析报告。

## 九、暂时不要做的事

1. 不要立刻训练语义级模型。
   - 语义单元切分和双层解码依赖高质量知识单元、正文和语义序列数据。现在数据底座还没稳，先做会变成空转。

2. 不要把知识单元插入 PDF 抽取中间流程。
   - 这会破坏现有 7 阶段管线的清晰边界。

3. 不要把标签当结构规则用。
   - 标签只能帮助检索和粗聚合，不能替代 `kind`、`domains`、`taxonomy_terms`、`relations`。

4. 不要绕过质检直接写 canonical 表。
   - 外部导入也必须经过对齐、合并、质量检查和图完整性检查。

5. 不要优先扩音频、视频等复杂多模态。
   - 正文层第一版先支持 Markdown 文本和图片，公式、表格沿用现有 Markdown 渲染能力；音频和视频延后。

## 十一、完成后的项目形态

如果上述三个月计划完成，OKM 会从“能抽取和展示图谱”推进到“能稳定支撑 AI 原生知识系统原型”：

1. 教材 PDF 可以进入 TypeScript 管线形成可追溯 KG。
2. Obsidian 笔记和外部知识单元可以导入并对齐到 KG。
3. 每个节点可以作为完整知识单元被读取：节点身份、关系、证据、卡片、正文、媒体、原文片段都在一个 API 中。
4. Viewer 不只是看图，还能看一个知识单元的完整上下文。
5. 上层生成系统可以按知识单元和关系路径做语义规划。
6. 研究上可以开始回答一个明确问题：对象级知识系统是否比普通文本片段检索更可靠、更可追溯、更适合教育生成。

## 十二、近期第一步

建议下一步直接从 `world_node_bodies` 开始。原因很简单：它是后面所有能力的共同依赖，而且当前代码已经有知识单元 API、Viewer Markdown 渲染、证据图片解析和正式正文生成入口，改动可以比较小步、比较稳。

第一步任务可以拆成一个最小提交：

1. 在 `schemas/pg/knowledge_store.sql` 增加 `world_node_bodies`。
2. 新增正文结构规则。
3. 更新 `ApiUnitBody`。
4. 更新 `loadUnit`，优先读取正文表。
5. 写一个服务端查询测试或纯逻辑测试。
6. 确认 Viewer 仍能展示旧节点，并能展示一条手工插入的正文记录。

这一步完成后，再进入正文生成和 Obsidian 导入，会顺很多。
